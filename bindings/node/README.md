# virtx for Node

Node bindings for virtx, built with [napi-rs](https://napi.rs): the same `ConsoleClient`,
`ImageClient`, `Recipe`, `Directory` and host mount as the Rust crate, camelCased, with every call that
waits returning a `Promise`.

```js
const { ConsoleClient, Directory, HostMount, Recipe } = require('@brekkylab/virtx')

const mount = new HostMount(new Directory().withFile('SKILL.md', '...'), '/tmp/skill')

const console_ = await ConsoleClient.builder()
  .cmd(['virtx-uvm'])
  .image(new Recipe('python:3.12-slim-trixie').step('pip install duckdb'))
  .mountReadonly(mount, '/skills/example')
  .mount('./artifacts', '/artifacts')
  .network(false)
  .vcpus(2)
  .memoryMib(2048)
  .build()

try {
  const result = await console_.exec(['sh', '-c', 'ls /skills/example'], 10_000)
  console.log(result.code, result.stdout.toString())
} finally {
  await console_.close()
}
```

A command's output can also be read while it runs. `execStream` yields what arrived since the
last chunk, the last one carrying the exit `code`; `spawn` leaves a command running as a `Job`
whose output you poll, while the console takes other calls:

```js
for await (const chunk of console_.execStream(['sh', '-c', 'make test'], 600_000)) {
  process.stdout.write(chunk.stdout)
}

{
  await using server = await console_.spawn(['python', '-u', '-m', 'http.server', '8000'])
  console.log((await server.poll(1000)).stdout.toString()) // what it has written so far
  // ... test against it
} // Leaving the block discards the job: killed, and let go of by the server.
```

The server holds a job until the poll that carries its `code`, up to a bound on how many it
holds. `await using` needs a Node with `Symbol.asyncDispose` (24 and later); elsewhere, and for
a job that should outlive the code that started it, `await job.discard()` ends it. If the `Job`
itself was let go of, `console_.job(id)` makes another handle from the id it had.

Leaving a `for await` early (`break`, `return`, a throw) kills the stream's command, as does
garbage collection of a stream nothing iterates any more.

Without `.cmd(..)` a console runs `virtx-uvm` from the `bin` directory of virtx's cache
(`$VIRTX_HOME`, or the host's cache directory: see [Cache](https://github.com/brekkylab/virtx#cache)).

An image can also be built ahead of the session that runs on it, and then named by its ref or
its digest:

```js
const { ImageClient, ImageSource, Recipe } = require('@brekkylab/virtx')

const images = await ImageClient.tryNew()
const built = await images.build(new Recipe('alpine:3.20').step('apk add jq'), 'myimg:latest')
for (const image of await images.list()) console.log(image.digest, image.refs)
await images.close()

const console_ = await ConsoleClient.builder().image(ImageSource.digest(built.digest)).build()
```

A `ConsoleClient` from this package can be handed to an [ailoy](https://github.com/brekkylab/ailoy)
agent as is (`new AgentBuilder(...).console(console_)`): the agent shares its session, taking
turns with your own calls one at a time, and `close()` ends the session for both.

## Errors

Every error carries a `code`, the way Node's own carry `ENOENT`:

| `code` | When |
|---|---|
| `TIMED_OUT`, `NOT_FOUND`, `UNKNOWN_JOB`, … | the console or image server refused, with virtx's name for its answer |
| `CONSOLE_REFUSED` | the server refused with a number this virtx has no name for |
| `CONSOLE_BROKEN` | the channel to the server is gone |
| `VIRTX_ERROR` | anything else from virtx, such as a console that could not be built |
| `INVALID_ARG` | a spent builder, a mounted `Directory`, a negative offset |
| `NotFound`, `InvalidInput`, … | a filesystem error, by its `io::ErrorKind` |

A `TIMED_OUT` from `exec`, a job's `poll` or a stream also carries what the command wrote until
it was killed, as `err.stdout` and `err.stderr` (Buffers) and `err.truncated`.

## Building

The `mount` feature is on by default and needs the host's FUSE provider, as the crate
does — see the top-level README.

```sh
cd bindings/node
npm install
npm run build        # or build:debug; writes index.js, index.d.ts and virtx.<platform>.node
npm test
```

`index.js` and `index.d.ts` are generated by the build. The crate's other features pass
through: `npm run build -- --features s3,notion`.

The console tests at the end of `__test__/index.spec.mjs` need a console server, named by
`$VIRTX_CONSOLE`; without one they are skipped.
