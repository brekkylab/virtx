Traffic crosses a sandbox in two directions, set separately:

- **Network** is the way out: connections the guest opens, such as `apk add` or an API call.
- **Ports** are the way in: connections to a service listening in the guest, such as a web server or a database.

[Client ports](#client-ports) are a third way, the reverse of ports: connections the guest opens to a service on your machine.

Both are set when the sandbox is created.

## Network

`network` is on by default.
The guest reaches public addresses, but not this host's loopback or private addresses.
Pass `network=False` to `create_sandbox` to block its outbound connections and name lookups, for code that should not talk to anything.

<Tabs syncKey="lang">
<TabItem label="Python">

```python
sandbox = await client.create_sandbox("alpine:latest", network=False)
```

</TabItem>
<TabItem label="Node.js">

```js
const sandbox = await client.createSandbox('alpine:latest', { network: false })
```

</TabItem>
<TabItem label="Rust">

```rust
let sandbox = client
    .create_sandbox(&SandboxCreateArgs::new("alpine:latest").network(false))
    .await?;
```

</TabItem>
</Tabs>

## Ports

A port carries plain TCP, so you can reach any service that listens on one: a web server, SSH, a VNC desktop, a database, or your own protocol.
virtx passes the bytes through without looking at them.

To reach a sandbox's port, use a `PortForwarder`.
It forwards the port to an address on your machine, and you connect to that address.

1. Pass `ports` to `create_sandbox` to open those ports in the sandbox.
2. Each one comes back in `sandbox.ports`.
3. `PortForwarder.open` takes the sandbox and the port, and gives you a local address, such as `127.0.0.1:54123`, that any TCP client can connect to.

How the forwarding works depends on where the server runs:

- **A server on your machine**, started with `Client.spawn`, already listens on a local address for each port, the port's `url`, so the forwarder just gives you that address.
- **A server over HTTP** is reached through a WebSocket.
  The forwarder listens on a local port, and opens a WebSocket to `/sandboxes/{id}/ports/{port}` for each connection made to it, with the client's credentials.
  The server passes the bytes between that WebSocket and the port in the sandbox.

<img src={portForwarding.src} width={portForwarding.width} height={portForwarding.height} alt="The PortForwarder opens a port on your machine's loopback, 127.0.0.1:<port>, and carries each connection to it in a WebSocket to ws://…/sandboxes/<id>/ports/8000 on the virtx server, which connects to port 8000 in the sandbox it runs." />

Because everything goes through the server's own HTTP address, the server's machine needs no other port open.
A sandbox found again with `get_sandbox`, `list_sandbox` or `find_sandbox`, from this program or another, forwards its ports as the one `create_sandbox` answered does.

In the example below, the sandbox opens port 8000 and runs an HTTP server on it, and the forwarder makes it reachable at a local address that a browser or `curl` can open:

<Tabs syncKey="lang">
<TabItem label="Python">

```python
from virtx import PortForwarder

sandbox = await client.create_sandbox("alpine:latest", ports=[8000])
await sandbox.exec(["httpd", "-f", "-p", "8000"])  # started, left running

with PortForwarder.open(sandbox, 8000) as forwarder:
    print(f"http://{forwarder.address}")
```

</TabItem>
<TabItem label="Node.js">

```js
const { PortForwarder } = require('@brekkylab/virtx')

const sandbox = await client.createSandbox('alpine:latest', { ports: [8000] })
await sandbox.exec(['httpd', '-f', '-p', '8000']) // started, left running

const forwarder = PortForwarder.open(sandbox, 8000)
console.log(`http://${forwarder.address}`)
forwarder.close()
```

</TabItem>
<TabItem label="Rust">

```rust
let sandbox = client
    .create_sandbox(&SandboxCreateArgs::new("alpine:latest").port(8000))
    .await?;
sandbox.exec(&SandboxExecArgs::new(["httpd", "-f", "-p", "8000"])).await?; // started, left running

let forwarder = PortForwarder::open(&sandbox, 8000)?;
println!("http://{}", forwarder.address());
drop(forwarder);
```

</TabItem>
</Tabs>

Each entry of `sandbox.ports` names the guest's `port` and its `label`, in the order they were asked for.
A port given twice, or port `0`, is refused.

A connection made while nothing listens on the port in the guest is closed at once, as a closed port's would be: start the service before connecting.
Through a server over HTTP, the forwarder says what it saw: a connection whose WebSocket is refused, or closed before the port sent a byte, with the reason the server gave if it gave one, is kept as the forwarder's last error, and logged as a warning that names the port and what the server answered.
A port that took the connection and closed it without a word ends the same way, so the message says what happened to the connection, not what runs in the sandbox.
Read it after a connection dies with `forwarder.last_error` in Python, `forwarder.lastError` in Node.js and `forwarder.last_error()` in Rust: an error whose message names the port, with the `status` the server refused the WebSocket with, if it did.
It is the last failure, not whether the port is reached now: it is none until a connection fails, and none again once a later connection's port sends a byte, so a program that retries while its service starts reads none once one gets through.
The warning goes to the `virtx` logger in Python, as a `VirtxWarning` through `process.emitWarning` in Node.js, and to the `log` crate under the target `virtx` in Rust.

Ports are opened only when the sandbox is created, and stay open until it is removed.
Closing a forwarder stops forwarding on this machine; the port in the sandbox stays open, and another forwarder can reach it again.

A server on this machine answers each port with a loopback address already, which a TCP client can also reach as it is.
A server over HTTP answers a URL that only a `PortForwarder` opens, so use one either way.

## What a port is for

A port in `ports` is a number, or a spec with a `label` of up to 128 characters saying what it is for.
The label comes back with the port wherever the sandbox is found again, so it is what tells its ports apart there:

<Tabs syncKey="lang">
<TabItem label="Python">

```python
from virtx import PortSpec

sandbox = await client.create_sandbox(
    "node:22",
    ports=[PortSpec(5173, label="dev server")],
)

found = await client.get_sandbox(sandbox.id)
print(found.ports[0].label)  # dev server
```

</TabItem>
<TabItem label="Node.js">

```js
const sandbox = await client.createSandbox('node:22', {
  ports: [{ port: 5173, label: 'dev server' }],
})

const found = await client.getSandbox(sandbox.id)
console.log(found.ports[0].label) // dev server
```

</TabItem>
<TabItem label="Rust">

```rust
let dev_server = PortSpec::new(5173).label("dev server");
let sandbox = client
    .create_sandbox(&SandboxCreateArgs::new("node:22").port(dev_server))
    .await?;

let found = client.get_sandbox(sandbox.id()).await?;
println!("{:?}", found.info().ports[0].label); // Some("dev server")
```

</TabItem>
</Tabs>

## Client ports

Client ports are ports the other way round: a process in the sandbox reaches a TCP port on your machine, such as a browser's debugging port or `adb`'s server, while the service stays where it is.

1. Pass `client_ports` to `create_sandbox`. Inside the sandbox, each one is reached at `10.0.2.2:<port>`.
2. `ClientPortForwarder.open` takes the sandbox and the port, and carries each connection a process makes to it to `127.0.0.1:<port>` on your machine, or to the `host:port` you give it, for as long as you hold the forwarder.

How it is carried depends on where the server runs:

- **A server on your machine**, started with `Client.spawn`, connects to `127.0.0.1:<port>` itself, for as long as the sandbox lives. The forwarder only checks that the sandbox was made with the port, and another target is refused.
- **A server over HTTP** is reached through a WebSocket, as a port is the other way.
  The forwarder keeps one open to `/sandboxes/{id}/client-ports/{port}`.
  When a process connects, the server tells the forwarder over it, and the forwarder connects to the target on your machine and carries the bytes; it opens another WebSocket at once for the next connection.

<img src={clientPortForwarding.src} width={clientPortForwarding.width} height={clientPortForwarding.height} alt="A process in the sandbox connects to 10.0.2.2:9222. The virtx server carries the connection in a WebSocket to ws://…/sandboxes/<id>/client-ports/9222, which the ClientPortForwarder on your machine holds open, and the forwarder connects it to 127.0.0.1:9222." />

The process's `connect` waits until the target is reached, and succeeds then.
Over HTTP it is refused, as one to a port nothing listens on is, when no forwarder is open, when the target is not reached, or when no forwarder takes it within a few seconds.
`10.0.2.2` at a port the sandbox was not made with is refused too: it never reaches the server's own network.
Client ports, like ports, do not need `network`.

In the example below, the sandbox has no network, and reads what a browser started on your machine with `--remote-debugging-port=9222` says about itself:

<Tabs syncKey="lang">
<TabItem label="Python">

```python
from virtx import ClientPortForwarder

sandbox = await client.create_sandbox("alpine:latest", network=False, client_ports=[9222])

async with await ClientPortForwarder.open(sandbox, 9222):
    await sandbox.exec(["wget", "-qO-", "http://10.0.2.2:9222/json/version"]).complete(print=True)
```

</TabItem>
<TabItem label="Node.js">

```js
const { ClientPortForwarder } = require('@brekkylab/virtx')

const sandbox = await client.createSandbox('alpine:latest', { network: false, clientPorts: [9222] })

const forwarder = await ClientPortForwarder.open(sandbox, 9222)
await sandbox.exec(['wget', '-qO-', 'http://10.0.2.2:9222/json/version']).complete({ print: true })
forwarder.close()
```

</TabItem>
<TabItem label="Rust">

```rust
let sandbox = client
    .create_sandbox(&SandboxCreateArgs::new("alpine:latest").network(false).client_port(9222))
    .await?;

let forwarder = ClientPortForwarder::open(&sandbox, 9222, None).await?;
let fetch = ["wget", "-qO-", "http://10.0.2.2:9222/json/version"];
sandbox.exec(&SandboxExecArgs::new(fetch)).complete(true).await?;
drop(forwarder);
```

</TabItem>
</Tabs>

`ClientPortForwarder.open` answers once the port is taken, so a process started after it reaches the port at once.
A port the sandbox was not made with is refused with `404`.

To carry the connections somewhere else than `127.0.0.1:<port>`, such as a device on your network, give the target, `host:port`.
The sandbox still sees the port it was made with:

<Tabs syncKey="lang">
<TabItem label="Python">

```python
forwarder = await ClientPortForwarder.open(sandbox, 9222, "192.168.0.20:9222")
```

</TabItem>
<TabItem label="Node.js">

```js
const forwarder = await ClientPortForwarder.open(sandbox, 9222, '192.168.0.20:9222')
```

</TabItem>
<TabItem label="Rust">

```rust
let forwarder = ClientPortForwarder::open(&sandbox, 9222, Some("192.168.0.20:9222")).await?;
```

</TabItem>
</Tabs>

The forwarder works for any sandbox with the port, made by this program or found again with `get_sandbox`, `find_sandbox` or `list_sandbox`, and several forwarders, of one program or of several, may take a port at once: each connection goes to one of them.
Closing the forwarder, or dropping it in Rust, lets the port go, and closes the connections it carries.
It also ends once the sandbox is removed: `wait_closed()` waits for that and answers why, a `404` once the sandbox is gone (`waitClosed()` in Node.js).
What fails on the way, such as a target not reached, is logged as a warning, as a forwarded port's failures are.

A client port gives the sandbox's processes whatever the program behind it gives: a browser's debugging port reaches everything that browser is signed in to, and `adb`'s server reaches the device.
Hand it only a port you would let that code use.
For uses of each, see [Driving your browser from a sandbox](/docs/guides/your-browser/) and [Driving an Android device from a sandbox](/docs/guides/android/).
