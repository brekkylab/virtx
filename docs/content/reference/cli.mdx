The `virtx` command does to a server's images what `docker` does to its own. The Python and Node.js packages install it, as `libvirtx_core` carries it, and the [virtx repository](https://github.com/brekkylab/virtx) builds it as a binary of its own:

```sh
uvx virtx images                 # or `pip install virtx`
npx @brekkylab/virtx images      # or `npm install -g @brekkylab/virtx`
cargo install --path virtx-cli   # in the repository: -> ~/.cargo/bin/virtx
```

| Command | What it does |
| --- | --- |
| `virtx build -t NAME[:TAG] [PATH]` | Builds an image from the Dockerfile in `PATH`, `.` by default, or the one `-f` names. The log goes to stderr and `NAME:TAG sha256:…` to stdout. |
| `virtx images` | Lists images. |
| `virtx inspect IMAGE…` | Prints images as JSON, each by a ref (`name:tag`), image ID or digest. |
| `virtx tag SOURCE TARGET[:TAG]` | Points a ref at an image, moving the ref if it is in use. |
| `virtx rmi IMAGE…` | Untags refs, removing an image with its last ref, or removes images by image ID or digest with every ref on them. |
| `virtx pull NAME[:TAG]` | Pulls an image from a registry, tagged as it is named. |
| `virtx push NAME[:TAG]` | Pushes an image to the registry its ref names. |
| `virtx save -o FILE IMAGE` | Writes an image to an OCI archive. |
| `virtx load -i FILE -t NAME[:TAG]` | Tags the image in an OCI archive, uploading what the server lacks. |
| `virtx image prune` | Removes every image no ref points at and no sandbox uses. |

Each command is also `virtx image <command>`, with `ls` and `rm` for `images` and `rmi`. A registry that wants credentials gets them with `-u USER`, its password or access token read from stdin, or `--token-stdin` for a bearer token. Ctrl-C during a build, pull or push cancels the job.

```sh
virtx build -t jq:latest .
virtx tag jq:latest ghcr.io/me/jq:1
echo "$GHCR_TOKEN" | virtx push -u me ghcr.io/me/jq:1
virtx save -o jq.tar jq:latest
virtx rmi jq:latest
```

## Which server

Without options, the command starts `virtx-stdio` of its own version, fetched into the cache the first time, or the program `--server` (`$VIRTX_STDIO`) names. `--host URL` (`$VIRTX_HOST`) reaches a server over HTTP instead, with `$VIRTX_TOKEN` as its bearer token; the token comes from the environment alone, so it is never on a command line. `--project NAME` (`$VIRTX_PROJECT`) names the project the requests belong to, a project of the user's by its name or any by its id, sent as the `virtx-project` header; without it, the requests are in the user's own, `default`. `--host` and `--server` together are refused; otherwise a flag wins over the environment and a host over a program, so `--server` starts its program with `$VIRTX_HOST` set, and `$VIRTX_HOST` is reached with `$VIRTX_STDIO` set. See [Hello world](/docs/hello-world/#run-it) for the two servers.

## Signing in

The `virtx` command also signs a person in, to virtx cloud or to the OpenID Connect provider of a virtx server, for a client to send the session's token.

| Command | What it does |
| --- | --- |
| `virtx login [URL]` | Signs in: it shows a code and a page to approve it at, and opens the page in a browser where there is one. |
| `virtx token` | Prints a token of the session, refreshed as needed; `--json` prints `{"token", "expires_in"}`, as the SDKs read it. |
| `virtx whoami` | Says who is signed in. |
| `virtx logout` | Signs out: the session is forgotten on this machine, and where it was signed in to is asked to end it. |

The `virtx` the Python and Node.js packages install signs in to virtx cloud alone. The one built from `virtx-cli/` signs in to both: a command is of the provider it names; naming none, of virtx cloud with `--domain`; and otherwise of what was signed in to last, or of virtx cloud where nothing was.

### virtx cloud

The page `virtx login` shows is the console's. `--domain` (`$VIRTX_DOMAIN`) names where virtx cloud is, `virtx.sh` by default.

`virtx token` prints the session's ID token, which lasts at most 15 minutes. The token names no project: virtx cloud takes it with the project each request names by its ID. `virtx logout` forgets the session on this machine whatever virtx cloud answers; if virtx cloud could not be told, the command says so and exits with an error, and the session ends there as it expires.

The session is kept in `~/.config/virtx/<domain>.token` and `<domain>.access`. On Linux and macOS they are readable by their owner alone.

A client made by [`Client.from_env()`](/docs/reference/api/#client) authenticates with `$VIRTX_API_KEY` if it is set. Without one and with `$VIRTX_PROJECT` set to a project's ID, it authenticates as the person signed in, with every request in that project. It runs `virtx token --json` for each token, so the `virtx` the package installs serves it with no other program. The console shows a project's ID on the project's API keys page.

```sh
virtx login
export VIRTX_PROJECT=<the project's ID>
```

### A server's provider

`virtx login <the server's URL>` asks the server which provider to sign in to and as which client: the `issuer` and `client_id` of its `oidc`. `--issuer` (`$VIRTX_OIDC_ISSUER`) and `--client-id` (`$VIRTX_OIDC_CLIENT_ID`) name the two without asking a server, and `--client-secret` (`$VIRTX_OIDC_CLIENT_SECRET`) gives the secret of a provider that has one for its public clients.

`virtx token` prints the ID token, which the server checks against the provider's keys. `virtx logout` asks the provider to end the session, where the provider takes that.

The session is kept under `~/.config/virtx/`. The refresh token is in the OS's keychain, or in a file where the keychain cannot be used, and the ID token last issued is in a file. The files are named for the client and the provider: `virtx@idp.example.token` and `virtx@idp.example.id` for the `oidc` of the server in Hello world's [On your own server (TCP)](/docs/hello-world/#on-your-own-server-tcp). On Linux and macOS they are readable by their owner alone.
