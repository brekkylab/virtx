virtx has four resources: images to boot, sandboxes to run commands, snapshots to keep what a sandbox writes over its image, and volumes to keep files apart from a sandbox.

| Resource | What it is | Made and read with |
| --- | --- | --- |
| Image | A manifest and layers from which a sandbox boots, under a tag such as `jq:latest`. | `build_image`, `pull_image`, `push_image`, and `commit_image` of a sandbox; list, tag, remove, download, and upload through the server's OCI registry. |
| Sandbox | A VM booted from an image, on a snapshot if given, with its own disk and volumes mounted into it. It stops after a time unused, or on request, and starts again as it was left, until deleted. | `create_sandbox`, `get_sandbox`, `find_sandbox`, `list_sandbox`, `start_sandbox`, `stop_sandbox`, `remove_sandbox`, `exec_sandbox`. |
| Snapshot | The writable layer of a sandbox's root filesystem, kept under a name. A sandbox made on it starts with the changes in it and writes into it. | `create_snapshot`, `get_snapshot`, `list_snapshot`, `remove_snapshot`; its files over WebDAV. |
| Volume | Named storage mounted into sandboxes, with remote sources such as Notion or Google Drive mounted inside it. | `create_volume`, `get_volume`, `list_volume`, `remove_volume`, and `*_volume_mount`; its files over WebDAV. |

These are the Python and Rust names. Node.js uses camelCase, such as `createSandbox`.

## Lifecycle

Build or pull an image, then create a sandbox from its tag or digest. Building, pulling, pushing, and committing images, and running sandbox commands, start [jobs](/docs/concepts/jobs/).

A sandbox keeps its files when it stops. Starting it again restores its files under the same id, but does not restore its processes. Removing it deletes its disk. An ephemeral sandbox is deleted when it stops; `auto_delete_days` can delete a sandbox after it has been stopped and unused.

A snapshot holds what a sandbox on it writes over its image, so what one sandbox installed the next one finds. While a sandbox holds it, its files are the sandbox's: reading them, and removing the snapshot, are refused until the sandbox is removed, the removal with `409`, code `in_use`. `create_snapshot` without a name lets the server pick one; its `disk_gib` is how much a sandbox on the snapshot may write over its image.

A volume can be mounted into multiple sandboxes and stays when those sandboxes are removed; on virtx cloud, one node at a time writes to it. A remote source is mounted inside a volume with `create_volume_mount(volume, path, source)`, the source a `NotionSource`, `GdriveSource`, or `OnedriveSource`; it is read-only, so copy a file out of it into the volume to change it. Commit a sandbox to an image to let other sandboxes boot from what it wrote.

## Sandbox options

`create_sandbox` takes an image tag or digest and these options, named here as in Python:

| Option | Default | What it does |
| --- | --- | --- |
| `snapshot` | none | A snapshot, by name, for its root filesystem's writable layer; without one, what it writes over its image goes when it is removed. |
| `name` | none | A name `find_sandbox` finds the sandbox by. |
| `ephemeral` | `False` | Deletes the sandbox when it stops. |
| `auto_stop_minutes` | 15 | Stops the sandbox after that long unused: no command running in it and no connection open through its ports. Listing its jobs or reading their logs does not count as use. Acted on by virtx cloud and the HTTP server, not the stdio server; see [Keep work](/docs/guides/keep-work/#stop-and-start). |
| `auto_delete_days` | 30 | Deletes the sandbox after that many days stopped and unused; `"never"` keeps it. |
| `disk_gib` | 2 | The size of its disk; `0` is refused. |
| `network` | `True` | `False` blocks its outbound connections; its ports still work. |
| `ports` | none; virtx cloud adds 5900 | Ports in it to reach from outside; see [Ports](/docs/guides/ports/). |
| `vcpus` | 2 on virtx cloud; 4 on your own server | Its CPUs. virtx cloud's default quota allows up to 8 for one sandbox. |
| `memory_mib` | 4096 | Its memory, in MiB. virtx cloud's default quota allows up to 16384 for one sandbox. |
| `gpu`, `gpu_memory_mib` | none | A GPU; see [GPU](/docs/guides/gpu/). |
| `volumes` | none | Volumes mounted at paths in it, read-only if asked; see [Keep work](/docs/guides/keep-work/). |

On virtx cloud, a sandbox's page in the console changes the sizes it was made with: vCPUs and memory while it is stopped, and the disk, which only grows, running or stopped. Each change applies as the sandbox next starts, its files kept.

On virtx cloud, an organization's default quotas allow 50 running sandboxes, with 100 vCPUs and 200 GiB of memory among them. Storage is 50 GiB of sandbox disks, 50 GiB of volumes and 20 GiB of images. A request that would go past one is refused with `429`, code `quota`.

See [Keep work](/docs/guides/keep-work/) for sandbox and volume lifecycles, and [Images](/docs/guides/images/) for image management.
