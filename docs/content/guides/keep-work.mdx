## Stop and start

A sandbox stops after `auto_stop_minutes` unused, or when you call `stop_sandbox`, and keeps its disk. Starting a command in it, or calling `start_sandbox`, starts it again under the same id with its files as they were left. Its processes are not restored. On virtx cloud, the console shows a running sandbox's files in its Files tab, read-only.

`remove_sandbox` deletes the sandbox and its disk. A sandbox made with `ephemeral=True` is deleted when it stops. `auto_delete_days` deletes a stopped sandbox once it has gone that many days unused; `"never"` keeps it until it is explicitly deleted (`'never'` in Node.js, `Some(None)` in Rust).

`auto_stop_minutes` and `auto_delete_days` are acted on by servers that keep running: virtx cloud and `virtx-server-tcp`, the HTTP server you run yourself. The stdio server, `virtx-stdio`, lives as long as the client process that spawned it: its sandboxes stop when that process exits, and it records both options without acting on them. An ephemeral sandbox it left behind is deleted the next time it starts.

Give a sandbox a `name` and use `find_sandbox` to find it without keeping its id:

```python
sandbox = await client.create_sandbox("jq:latest", name="dev")
...
sandbox = await client.find_sandbox("dev")  # tomorrow: what it installed is there
```

## Delete on leaving a block

A sandbox used for one block can be deleted on leaving it. Python uses `async with`; Node.js uses `await using`, in a runtime that supports it. Rust has no such block: the program calls `remove_sandbox` when it is done. A sandbox already deleted in the block stays deleted.

Read a command's log through its end inside the block. Awaiting `exec_sandbox` returns once the command has started, and leaving the block deletes the sandbox it runs in.

<Tabs>
<TabItem label="Python">

```python
async with await client.create_sandbox("jq:latest") as sandbox:
    async for entry in client.exec_sandbox(sandbox.id, ["echo", "hi"]):
        print(entry.entry)
```

</TabItem>
<TabItem label="Node.js">

```js
{
  await using sandbox = await client.createSandbox('jq:latest')
  for await (const entry of client.execSandbox(sandbox.id, ['echo', 'hi'])) {
    if ('stdout' in entry) console.log(entry.stdout)
  }
}
```

</TabItem>
<TabItem label="Rust">

```rust
let sandbox = client.create_sandbox(&SandboxCreateArgs::new("jq:latest")).wait()?;
let mut log = client.exec_sandbox(&sandbox.id, &SandboxExecArgs::new(["echo", "hi"])).log();
while let Some(entry) = log.wait_next() {
    if let SandboxJobEntry::Stdout(line) = entry?.entry {
        println!("{line}");
    }
}
client.remove_sandbox(&sandbox.id).wait()?;
```

</TabItem>
</Tabs>

## Start on a snapshot

A snapshot is the writable layer of a sandbox's root filesystem, kept under a name. A sandbox made on one starts with the changes in it and writes into it, so what one sandbox installed the next one finds, with no image to commit. While a sandbox holds the snapshot, its files are the sandbox's: reading them, and removing the snapshot, are refused until the sandbox is removed.

```python
await client.create_snapshot("dev")
sandbox = await client.create_sandbox("jq:latest", snapshot="dev")
```

Without a name, `create_snapshot` lets the server pick one; its `disk_gib` is how much a sandbox on the snapshot may write over its image. The snapshot's files are read and written from the client as a volume's are, with `Snapshot("dev")` as the root; see [below](#read-and-write-files-without-a-sandbox).

## Commit an image

To start other sandboxes from what a sandbox made, commit it to an image. The image contains its original image with what it wrote to its own disk as one more layer; what it wrote into volumes stays in the volumes. Any number of sandboxes can boot from it once the commit's log has ended without an error.

```python
async for entry in client.commit_image(sandbox.id, "dev:v1"):
    print(entry.entry)  # ... then ImageJobEnd(digest=...) or ImageJobEnd(error=...)
```

See [Images](/docs/guides/images/) for tags, digests, and registry operations.

## Mount a volume

A volume is storage kept apart from a sandbox. It can be mounted into any number of sandboxes at paths you choose, read-only if requested, and stays when those sandboxes are removed. On virtx cloud, a volume mounted to be written is held by the node its sandbox runs on. A sandbox on another node that mounts it to write is refused with `409`, code `in_use`, until the first has stopped. Read-only mounts are not held.

```python
from virtx import SandboxVolume

await client.create_volume("data")
sandbox = await client.create_sandbox(
    "jq:latest", volumes=[SandboxVolume(volume="data", path="/data", readonly=False)]
)
```

## Read and write files without a sandbox

Each file request names its root, a `Volume` or a `Snapshot`, and a path relative to it. These requests do not need a sandbox:

```python
from virtx import Volume

volume = Volume("data")
await client.create_dir_all(volume, "in")
await client.write_file(volume, "in/notes.txt", b"ship the release")
for entry in await client.read_dir(volume, "in"):
    print(entry.name, entry.metadata.size)
print(await client.read_text(volume, "in/notes.txt"))
```

`create_dir` creates a directory whose parent exists; `create_dir_all` creates parents as needed. `read_dir` lists entries and their metadata. `read_file` reads bytes, optionally from an offset for a given length, and `read_text` reads a UTF-8 file as text. `write_file` writes a whole file; its parent directory must exist.

Use `stat_file` to obtain file metadata. Pass its `etag` as `if_match` to `write_file` to write only while the file still has that tag. A changed tag causes the write to be refused with `412`.

`exists`, `is_file`, and `is_dir` say whether a path is there and what it is. `rename_file` moves files and `copy_file` copies them; each refuses an occupied destination unless `overwrite=True`. `remove_file` removes a file, or a directory with everything in it, and refuses a missing path with `404` unless `missing_ok=True`. The same file API is available in Node.js with camelCase names.
