A sandbox's root filesystem is its image below, read-only, and a disk of its own above, where everything it writes goes.
That disk lasts until the sandbox is deleted.
While nothing uses the sandbox, the server **parks** it: its VM is stopped, and its disk is kept.
The next command or request to its files boots the VM again, under the same id, with its files as it left them.

The example on this page follows an AI agent's task, with two directories in the sandbox:

- `/attachments`: the files the user gave the agent.
- `/artifacts`: the files the agent made.

## Make a sandbox to keep

`create_sandbox` makes a sandbox that is kept already.
Give it a `name` to find it again by, with `find_sandbox`, instead of keeping its id; a name another sandbox has is refused with `409`, `exists`.

This makes a sandbox for task 42 and writes the user's input into `attachments`.
`write_file` writes a whole file, and its parent directory must exist.

<Tabs syncKey="lang">
<TabItem label="Python">

```python
sandbox = await client.create_sandbox("alpine:latest", name="task-42")
await sandbox.create_dir_all("attachments")
await sandbox.write_file("attachments/notes.txt", "ship the release on friday\n")
```

</TabItem>
<TabItem label="Node.js">

```js
const sandbox = await client.createSandbox('alpine:latest', { name: 'task-42' })
await sandbox.createDirAll('attachments')
await sandbox.writeFile('attachments/notes.txt', 'ship the release on friday\n')
```

</TabItem>
<TabItem label="Rust">

```rust
let args = SandboxCreateArgs::new("alpine:latest").name("task-42");
let sandbox = client.create_sandbox(&args).await?;
sandbox.create_dir_all("attachments").await?;
sandbox
    .write_file("attachments/notes.txt", "ship the release on friday\n", None)
    .await?;
```

</TabItem>
</Tabs>

A sandbox made for one block, with `async with` in Python or `await using` in Node.js, is deleted on leaving it: make one to keep without them.

## Run it, and leave it

The agent counts the words in the user's notes into `/artifacts`, and leaves the sandbox as it is.
Nothing needs stopping: once the job has ended and nothing else uses the sandbox, the server parks it.

<Tabs syncKey="lang">
<TabItem label="Python">

```python
cmd = ["sh", "-c", "mkdir -p /artifacts && wc -w /attachments/notes.txt > /artifacts/report.txt"]
async for _ in sandbox.exec(cmd):
    pass
```

</TabItem>
<TabItem label="Node.js">

```js
const cmd = ['sh', '-c', 'mkdir -p /artifacts && wc -w /attachments/notes.txt > /artifacts/report.txt']
for await (const _ of sandbox.exec(cmd)) {}
```

</TabItem>
<TabItem label="Rust">

```rust
let cmd = ["sh", "-c", "mkdir -p /artifacts && wc -w /attachments/notes.txt > /artifacts/report.txt"];
let mut log = sandbox.exec(&SandboxExecArgs::new(cmd)).log();
while let Some(entry) = log.next().await {
    entry?;
}
```

### What keeps its VM up

A sandbox is used while a job runs in it, while a connection through one of its [ports](/docs/guides/networks-ports/) is open, while a request to its [files](/docs/guides/reading-writing-files/) is answered, and while a terminal in it is typed in or runs a command; starting a job uses it too.
The server parks it once it has gone unused for a while, about a minute on `virtx-server-tcp` and the stdio server.
Getting or listing it does not use it.

A parked sandbox has no VM: what is kept of it is its disk.
Everything it wrote is on that disk, but what was left running in it apart from a job, such as a server started in the background, is not.
The next job, terminal or request to its files boots its VM again, and so takes as long as booting does.
A connection to one of its ports while it is parked is closed, as one to a port nothing listens on is, and does not boot it.

A sandbox's `running` stays `true` while it is parked.
It is `false` only once its VM has exited on its own, and never `true` again: such a sandbox takes no more jobs, refusing them with `409`, `ended`, and is kept until it is removed.

## Find it again, and carry on

`find_sandbox` finds a sandbox by its name, parked or not, and answers none when no sandbox has it: one never made, or deleted since.
Here the user adds a file to `attachments`, and the agent carries on with it; the write boots the sandbox if it was parked:

<Tabs syncKey="lang">
<TabItem label="Python">

```python
sandbox = await client.find_sandbox("task-42")
if sandbox is None:
    raise LookupError("task-42 was deleted")

await sandbox.write_file("attachments/todo.txt", "write the changelog\n")
async for entry in sandbox.exec(["ls", "/attachments", "/artifacts"]):
    print(entry.entry)
print(await sandbox.read_text("artifacts/report.txt"))
```

</TabItem>
<TabItem label="Node.js">

```js
const sandbox = await client.findSandbox('task-42')
if (!sandbox) throw new Error('task-42 was deleted')

await sandbox.writeFile('attachments/todo.txt', 'write the changelog\n')
for await (const entry of sandbox.exec(['ls', '/attachments', '/artifacts'])) console.log(entry)
console.log(await sandbox.readText('artifacts/report.txt'))
```

</TabItem>
<TabItem label="Rust">

```rust
let Some(sandbox) = client.find_sandbox("task-42").await? else {
    return Err("task-42 was deleted".into());
};

sandbox
    .write_file("attachments/todo.txt", "write the changelog\n", None)
    .await?;
let mut log = sandbox.exec(&SandboxExecArgs::new(["ls", "/attachments", "/artifacts"])).log();
while let Some(entry) = log.next().await {
    println!("{:?}", entry?.entry);
}
println!("{}", sandbox.read_text("artifacts/report.txt").await?);
```

</TabItem>

A sandbox booted again has its files as it left them, with anything it installed or changed, and boots the same image it was made from, even if that image's tag has moved since.
Its processes are not kept: nothing that ran in it runs again until something starts it.
Its volumes are mounted again and its ports opened again, at the URLs its making answered; the stdio server keeps those only for as long as it runs.

## Remove it

A sandbox is deleted by `remove`, or by the server once it has gone unused for long: `virtx-server-tcp`, the stdio server and virtx cloud delete one unused for 30 days.
Deleting one stops its VM if it is up, and removes its disk with everything it wrote; its volumes stay.
