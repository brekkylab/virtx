`virtx-server-tcp` is the virtx server for a team.
It runs on a machine of yours, keeps running, and serves every user your OpenID Connect provider signs in.
Each user works in projects of their own and those shared with them; see [Managing projects](/docs/guides/projects/).

To run sandboxes on your own machine for yourself alone, you need none of this: `Client.spawn()` starts a server for your program; see [Hello world](/docs/hello-world/).

## Install

Each [release](https://github.com/brekkylab/virtx/releases) carries the server as `virtx-server-tcp-<os>-<arch>.tar.gz`.
Unpack it into a directory of its own on the machine that should run the VMs, and run `virtx-server-tcp` from there: it finds what it needs beside it.
The machine must meet the [requirements](https://github.com/brekkylab/virtx#requirements) for running VMs.

## Configure

Write a `server.json`:

```json
{
  "listen": "127.0.0.1:8470",
  "home": "/var/lib/virtx",
  "oidc": { "issuer": "https://idp.example", "client_id": "virtx" }
}
```

Then start the server with it:

```sh
virtx-server-tcp serve --config server.json
```

| Field | What it sets |
| --- | --- |
| `listen` | The address and port the server listens on. |
| `home` | The directory where the server keeps everything its users create, sandboxes included: stopped and started again over it, the server has each sandbox it had, with what it wrote. Without it, the server uses `$VIRTX_HOME`, or a `virtx` directory in its user's cache directory. |
| `oidc` | The OpenID Connect provider users sign in with; see [Sign users in](#sign-users-in). |
| `origins` | The web pages allowed to call the server from a browser, such as `["https://app.example"]`. Without it, browsers are refused; programs are not affected. |
| `private_registries` | Registries on the server's machine or its private network that image jobs may reach, such as `["registry.internal:5000"]`; see [Pull and push](/docs/guides/images/#pull-and-push). Without it, jobs reach only registries on public addresses. |
| `registry_mirror` | A mirror of Docker Hub, such as `"mirror.gcr.io"`, that pulls of Docker Hub's images without credentials try first, a build's base among them; see [Pull and push](/docs/guides/images/#pull-and-push). Without it, they go to Docker Hub. |

`listen` and `oidc` are required, and the server does not start with a field it does not know.

The server serves HTTP, and TLS is left to whatever you put in front of it, as with any HTTP service.
Clients send a token over HTTPS to other machines, so serve it there over HTTPS, passing WebSocket connections through: [ports](/docs/guides/networks-ports/) are reached over them.
With it on the same machine, listen on `127.0.0.1`; listen on another address only for a proxy on another machine.

## Sign users in

The server lets nobody in by itself: every user signs in through an OpenID Connect provider you already use.

The server keeps no list of users: it takes everyone your provider signs in to the client you name, so allow only your team to use that client in the provider.
In your provider, register a public client that allows the device flow, and put the provider and the client in `oidc`:

| Field | What it sets |
| --- | --- |
| `issuer` | The provider's issuer URL. |
| `client_id` | The client you registered. |
| `username_claim` | Which claim of the user's ID token is their user name on the server. `email` by default, taken only once the provider has verified it. |
| `jwks_uri` | Where the provider's signing keys are, for a provider without a discovery document. Most providers need none. `virtx login` needs the discovery document, so with such a provider users get their token another way and connect with it as a bearer token, as the end of this page shows. |

The user name is how others add a user to their projects, so with the default, teammates add each other by email address.

## Connect to it

Each user signs in once with the `virtx` command, which `pipx` or `npx` runs without installing; to install it instead, see [CLI](/docs/reference/cli/).
It asks the server which provider to use, and shows a code to approve in the browser:

```sh
pipx run virtx login https://virtx.example            # uvx also works

# or

npx -y @brekkylab/virtx login https://virtx.example
```

Then a program connects with the token `virtx token` prints, which the client asks for again whenever it runs out:

<Tabs syncKey="lang">
<TabItem label="Python">

```python
from virtx import Client, CommandAuth

client = Client.connect("https://virtx.example", CommandAuth("pipx", ("run", "virtx", "token", "--json")))
```

</TabItem>
<TabItem label="Node.js">

```js
const client = Client.connect('https://virtx.example', {
  type: 'command',
  program: 'npx',
  args: ['-y', '@brekkylab/virtx', 'token', '--json'],
})
```

</TabItem>
<TabItem label="Rust">

```rust
use virtx::{Auth, Client};

let client = Client::connect(
    "https://virtx.example",
    Auth::Command { program: "pipx".into(), args: vec!["run".into(), "virtx".into(), "token".into(), "--json".into()] },
    None,
    [] as [(&str, &str); 0],
)?;
```

</TabItem>
</Tabs>

For a provider that gives its public clients a secret, pass it to `virtx login` with `--client-secret`.
A program that gets its token some other way passes it as it is, with `BearerAuth` in Python, `{ type: 'bearer', token }` in Node.js, or `Auth::Bearer` in Rust.

`virtx whoami` shows who is signed in, and `virtx logout` signs out; see the CLI's [Signing in](/docs/reference/cli/#signing-in).
Signed in to more than one provider, name the server's to `virtx token`: `virtx token --json --issuer https://idp.example --client-id virtx`.
