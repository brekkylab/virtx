---

Names here are Python's.
Node.js uses the same names in camelCase, such as `createSandbox` for `create_sandbox`, and Rust uses the same names as Python, except where noted.

What a call returns, once awaited where it is async, is named as Python has it.
The types share their names in all three: `list[Sandbox]` is `Sandbox[]` in Node.js, inside a `Promise`, and `Vec<Sandbox>` in Rust, inside a `Result`.

A call that starts a job, marked **job** below, is iterated for its log or awaited for the job; see [Running commands](/docs/guides/running-commands/#follow-a-job).
Its log, like a job's `log`, yields a `LogEntry` at a time.
`download_image` and `upload_image` yield `Progress` events, then one event carrying their output.

## Client

| Call | Returns | What it does |
| --- | --- | --- |
| `Client.spawn(program, args)` | `Client` | Starts a server as a child process and talks to it over its stdin and stdout. Without `program`, it starts `virtx-stdio` of the library's version, fetched into a cache the first time. Rust calls the no-program form `Client::spawn_virtx`. |
| `Client.connect(url, auth, headers)` | `Client` | Reaches a server over HTTP at its base `url`, sending `auth` and `headers` with every request. A token is sent over plain `http` only to this machine's loopback. |
| `Client.from_env()` | `Client` | Reaches virtx cloud, or the server `VIRTX_URL` names, as its [environment variables](#environment-variables) say: with `VIRTX_API_KEY`, as that key; with `VIRTX_ORG` and no key, as the person `virtx login` signed in, running `virtx token --json` for each token. Node.js calls it `fromEnv`. |
| `set_auth(auth)`, `set_headers(headers)` | `None` | Replace what every later request sends. |
| `clone()` | `Client` | Another hold of the same session. |
| `close()` | `None` | Lets go of this hold; the last one ends the session. Python's `aclose` does it off the event loop. |
| `ensure_virtx()` | `str`, its path | Fetches `virtx-stdio` into the cache ahead of `spawn`, without starting it. Node.js calls it `ensureVirtx`. |

## Images

See [Working with images](/docs/guides/images/).

| Call | Returns | What it does |
| --- | --- | --- |
| `build_image(recipe, reference)` | `ImageJob` | **Job.** Builds `recipe` and points `reference` at the result. |
| `pull_image(reference, auth)` | `ImageJob` | **Job.** Pulls `reference` from its registry. Without `auth`, anonymously. |
| `push_image(reference, auth)` | `ImageJob` | **Job.** Pushes the image `reference` points at to the registry it names. |
| `commit_image(sandbox, reference)` | `ImageJob` | **Job.** Makes an image of the sandbox `sandbox`, by its id or, in Python and Node.js, its `Sandbox`, as its [`commit`](#sandboxes) does. |
| `list_image()` | `list[ImageListOutputItem]` | Every tag on the server's images, with the digest it points at. |
| `tag_image(source, target)` | `None` | Points the tag `target` at the image `source` names, moving it if it is in use. |
| `untag_image(reference)` | `None` | Removes a tag, leaving the image. |
| `remove_image(reference)` | `None` | Removes the image and every tag on it in that name; refused while a sandbox uses it. |
| `download_image(reference, path)` | events, then `ImageDownloadOutput` | Writes the image to an OCI image layout tar archive at `path`. |
| `upload_image(path, reference)` | events, then `ImageUploadOutput` | Uploads the image in an OCI archive and points the tag `reference` at it. |
| `prune_image()` | `ImagePruneOutput` | Deletes images no tag points at and no sandbox uses, once they are an hour old. |

A `Recipe(base)` is chained with `.run(command)`, `.env(key, value)` and `.workdir(directory)`.
In Rust, `Recipe::new(base).step(..)` takes a `Step::run`, `Step::env` or `Step::workdir`, or a plain string as a `run` step, and `Recipe::from_dockerfile(text)` reads a Dockerfile.

## Sandboxes

See [Setting up sandboxes](/docs/guides/setting-sandboxes/) for the options `create_sandbox` takes.

| Call | Returns | What it does |
| --- | --- | --- |
| `create_sandbox(image, ...)` | `Sandbox` | Makes a sandbox of `image`, running, with the options given. |
| `list_sandbox()`, `get_sandbox(id)` | `list[Sandbox]`, `Sandbox` | The server's sandboxes, running or stopped, without their ports. |
| `find_sandbox(name)` | `Sandbox` or `None` | The sandbox made with the `name` given, without its ports, if one is. `undefined` in Node.js for none. |
| `start_sandbox(id)`, `stop_sandbox(id)` | `Sandbox` | A `Sandbox`'s `start` and `stop`, by its id. |

A sandbox keeps its disk, what it writes over its image, when its VM stops: it stops after `auto_stop_minutes` unused, or at `stop`, and starts again as it was left, under the same id, until it is deleted -- at `remove`, when it stops if it is `ephemeral`, and after `auto_delete_days` stopped and unused, which `"never"` turns off (`None` in Rust's `SandboxCreateArgs::auto_delete_days`).
Left out, the server picks them: 15 minutes and 30 days on `virtx-stdio` and `virtx-server-tcp`.

A `Sandbox` has its `id`, `name`, `image`, `state` (`"running"` or `"stopped"`), `ephemeral`, `auto_stop_minutes`, `auto_delete_days` and `used_at`, and its `ports` as `create_sandbox` and `start` answer them.
It carries its client, and acts on itself:

| Call | Returns | What it does |
| --- | --- | --- |
| `exec(cmd, stdin, timeout_ms)` | `SandboxJob` | **Job.** Runs `cmd`, an argv, starting the sandbox first if it is stopped. With `stdin`, its stdin stays open for `write_stdin`; with `timeout_ms`, it is killed when the time runs out. |
| `jobs()`, `job(id)` | `list[SandboxJob]`, `SandboxJob` | Its jobs. |
| `open_port(port, label, protocol, inbound)` | `SandboxPort` | Opens `port` in it, TCP unless `protocol` is `"http"`, kept in `ports`. With `inbound`, a list of `InboundRule`, its inbound rules are set as it opens. In Rust, `open_port(port)`, and the client's `open_sandbox_port_with(id, port, args)` for the rest. |
| `close_port(port)` | `None` | Closes `port`: its `url` reaches it no more. |
| `inbound(port)` | `PortInbound` | **virtx cloud.** The port's inbound rules, and its public `address` once it has one. |
| `set_inbound(port, rules)` | `PortInbound` | **virtx cloud.** Replaces the port's inbound rules with `rules`; `[]` lets in no one. |
| `start()` | `Sandbox` | Starts it if it is stopped, its VM booted over its disk as it was left, and answers it once it runs, with where its ports are now. |
| `stop()` | `Sandbox` | Stops it if it runs: its jobs end, and its disk is kept, or deleted with it if it is `ephemeral`. |
| `commit(reference)` | `ImageJob` | **Job.** Makes an image of it, its image with what it has written as one more layer, and points `reference` at it: of a running one as it is when the job starts, of a stopped one as it was left. |
| `remove()` | `None` | Deletes it: stops it if it runs, and removes its disk. Its volumes stay. |

Its [files](#files) are as its processes see them, while it runs; a stopped one's are refused with `409`, `stopped`.

In Rust, `Sandbox` answers `id()`, `name()` and `info()`, which holds the fields above.

A port in `create_sandbox`'s `ports` is a number, for TCP, or a `PortSpec(port, label, protocol, inbound)`; in Node.js, `{ port, label?, protocol?, inbound? }`.
An `InboundRule(source, description)` lets in `source`, an IPv4 or IPv6 CIDR or one address, which the server keeps as a CIDR.
A `PortInbound` has the `port`, its `rules`, and its `address` when it has one.
Inbound rules are virtx cloud's: a self-hosted server refuses `inbound` with `400`, and the desktop's port 5900 refuses them with `409`, `not_public`.
In Python and Rust the client has the same two calls as `get_sandbox_port_inbound(id, port)` and `set_sandbox_port_inbound(id, port, rules)`.

## Jobs

A job is a sandbox's process, from `exec`, or an image's build, pull or push.

### Sandbox jobs

A `SandboxJob`, from awaiting `exec` or from `job(id)`, has its `id`, `pid`, `cmd`, whether it is `running`, and once it has ended, its exit `code`.

| Call | Returns | What it does |
| --- | --- | --- |
| `get()` | `SandboxJob` | The job as the server has it now. |
| `log(after)` | `LogEntry`s | Its output, from its start or after entry `after`, until its end. |
| `signal(signal)` | `None` | Sends a signal, such as `"SIGTERM"`, to its process and every process it started. |
| `write_stdin(data, eof)` | `None` | Writes to the stdin of a job started with `stdin`, and closes it if `eof`. Await each write before the next. |
| `remove()` | `None` | Kills its process if it runs, and forgets the job. |

Code that holds only ids gets the job back with `get_sandbox(id)`, then its `job(id)`.
In Rust, `SandboxJob` answers `id()` and `info()`.

### Image jobs

| Call | Returns | What it does |
| --- | --- | --- |
| `list_image_job()`, `get_image_job(id)` | `list[ImageJob]`, `ImageJob` | The server's image jobs. |

An `ImageJob`, from awaiting `build_image`, `pull_image` or `push_image` or from `get_image_job(id)`, carries its client and acts on itself.
It has its `id`, its `kind`, the `reference` it points or pushes, whether it is `running`, and once it has ended, the `digest` it made or the `error` it failed with.

| Call | Returns | What it does |
| --- | --- | --- |
| `get()` | `ImageJob` | The job as the server has it now. |
| `log(after)` | `LogEntry`s | Its log, from its start or after entry `after`, until its end. |
| `remove()` | `None` | Cancels it if it runs, and forgets the job. |

In Rust, `ImageJob` answers `id()` and `info()`.

## Volumes

See [Mounting volumes](/docs/guides/mounting-volumes/).

| Call | Returns | What it does |
| --- | --- | --- |
| `create_volume(name)` | `Volume` | Makes an empty volume. Without a name, the server picks one. |
| `list_volume()`, `get_volume(name)` | `list[Volume]`, `Volume` | The server's volumes. |

A `Volume` has its `name` and `size`, and its [files](#files):

| Call | Returns | What it does |
| --- | --- | --- |
| `mount(path, source)` | `VolumeMountListOutputItem` | Mounts a remote store at `path` in it, read-only. |
| `mounts()` | `list[VolumeMountListOutputItem]` | The mounts in it, without their credentials. |
| `unmount(path)` | `None` | Takes a mount away, leaving its store as it is. |
| `remove()` | `None` | Deletes it and everything in it. |

## Files

A `Sandbox` and a `Volume` share these calls, each on its own files, by a path relative to its root such as `dir/file.txt`.

| Call | Returns | What it does |
| --- | --- | --- |
| `stat_file(path)` | `Metadata` | What is at `path`: its size, its modification time, and its `etag`. |
| `exists(path)`, `is_file(path)`, `is_dir(path)` | `bool` | Whether anything, a file, or a directory is at `path`. |
| `read_dir(path)` | `list[DirEntry]` | The entries of a directory, each with its `name` and `metadata`. |
| `read_file(path, offset, length)` | `bytes` | A file's bytes, all of them or a range. |
| `read_text(path)` | `str` | A whole UTF-8 file as text. |
| `write_file(path, content, if_match)` | `None` | Writes a whole file, whose parent directory must exist. With `if_match`, only while the file still has that `etag`. |
| `create_dir(path)` | `None` | Creates a directory whose parent exists. |
| `create_dir_all(path)` | `None` | Creates a directory and its parents, as `mkdir -p`. |
| `remove_file(path, missing_ok)` | `None` | Removes a file, or a directory with everything in it. With `missing_ok`, nothing being there is fine. |
| `rename_file(from_path, to_path, overwrite)` | `None` | Moves a file or directory; refused onto something that exists unless `overwrite`. |
| `copy_file(from_path, to_path, overwrite)` | `None` | Copies a file or directory, as `rename_file` replaces. |

## PortForwarder

See [Networks and ports](/docs/guides/networks-ports/).

| Call | Returns | What it does |
| --- | --- | --- |
| `PortForwarder.open(client, port)` | `PortForwarder` | Forwards a sandbox's port, as `ports` answers it, or the `url` answered for it, to an address on this machine's loopback. Given the port, a failed connection's error names its number. |
| `address`, `host`, `port` | `str`, `str`, `int` | Where it is reached. In Rust, `address()`. |
| `last_error` | `VirtxError` or `None` | Why the last connection that reached nothing in the sandbox failed -- its WebSocket refused, or closed before the port sent a byte, as when nothing listens there -- naming the port. Each is also logged as a warning. In Node, `lastError`; in Rust, `last_error()`. |
| `close()` | `None` | Stops forwarding; the port in the sandbox stays open. In Rust, dropping it does the same. |

## Errors

A call that fails raises `VirtxError` (Python, Node) or returns `virtx::Error` (Rust). It says
why, for a person, and where the server refused the request:

| Field | What it is |
| --- | --- |
| `status` | The HTTP status: `404` for what does not exist, `409` for what is in use or has ended, and the like. In Rust, `status()`. |
| `code` | The server's code for the refusal, such as `not_found`, `stopped` or `in_use`: what to branch on, rather than the message. In Rust, `code()`. |
| `body` | The response body, where the server's answer was not a JSON error. Python and Node only. |

## Environment variables

| Variable | Read by | What it does |
| --- | --- | --- |
| `VIRTX_CORE_LIB` | Clients | The `libvirtx_core` to open, when the program has not loaded one itself. |
| `VIRTX_STDIO` | `spawn`, CLI | A server to start as it is, in place of the fetched `virtx-stdio`. |
| `VIRTX_STDIO_VERSION` | `spawn`, CLI | Another version of `virtx-stdio` to fetch. |
| `VIRTX_DIST_URL` | `spawn`, CLI | Where releases are fetched from. |
| `VIRTX_HOME` | `spawn`, CLI | Where virtx keeps what it fetches on this machine. |
| `VIRTX_HOST` | CLI | A server's base URL, reached over HTTP in place of a server started here. |
| `VIRTX_TOKEN` | CLI | The bearer token sent to `VIRTX_HOST`. |
| `VIRTX_URL` | `from_env` | A server's base URL, reached in place of virtx cloud. |
| `VIRTX_API_KEY` | `from_env` | An API key of virtx cloud, sent as the bearer token. |
| `VIRTX_ORG` | `from_env` | An organization's ID, sent with every request as the `virtx-org` header. Without `VIRTX_API_KEY`, the client signs in as the person `virtx login` signed in. |
| `VIRTX_REGION` | `from_env` | Without `VIRTX_URL`, the cell of virtx cloud to reach, such as `apne2`. Without it, the cell nearest this machine, when `VIRTX_API_KEY` or `VIRTX_ORG` is set. |
| `VIRTX_DOMAIN` | `from_env`, CLI | Where virtx cloud is; `virtx.sh` by default. |
| `VIRTX_MINUTE_MS` | Server | How long a minute of a sandbox's `auto_stop_minutes` lasts, in milliseconds, and so a day of its `auto_delete_days`, 1440 of them. A minute by default; for tests that wait on a sandbox stopping. |
